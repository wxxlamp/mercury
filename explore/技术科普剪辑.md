# 技术科普怎么剪

先选一个能追踪的请求、文件或状态，写清它的起点、预期结果和实际结果。整段围绕“哪一步改变了结果”移动视线。每次引入组件之前，先给观众看现有路径在哪里遇到了问题。

## 让机制图与真实运行接得上

小盒子童鞋的网关片在 Ingress 段让拓扑退到背景，把终端和等待计数放到前景。作者给出实验条件和等待 30 秒的结果，随后观众可以回到拓扑，定位缺少控制器的那一环。这里最值得借的是**从示意图进入实证、再回到同一位置**的切法。[网关原片与实验说明](../reference/sources/nginx/)

| 观众此刻要判断什么 | 镜头怎么接 |
| --- | --- |
| 请求从哪儿出发，应该到哪儿？ | 先固定全景，摆清发送端、边界和接收端。给请求一个能在图和日志中认出的标记，镜头第一次走完整条路径时保持方向一致。 |
| 哪一次动作改变了状态？ | 在触发词上让对象实际移动或变形，保留变化前的记录供对照。需要读值才推近，值被哪一端采用就从哪一端接下一镜。先用点线跑通最难的一次交接，再加材质。[代码讲解镜头](../reference/vibe-motion/github/remotion-code-motion-explainer/) |
| 我怎么知道它真的发生了？ | 切到本期真实录屏或日志，同屏保留输入条件、标识和结果。连续等待可以压缩，中间标明经过的时间。看清结果后拉回原拓扑，让刚验证过的节点继续下一步。 |

## 试剪「请求明明写入了，为什么还会重试」

开场就让发送端显示“等待”，接收端却已有一条记录。倒回这个请求刚出发的一刻，保持两端的位置。先跟请求到写入处，再跟回执往回走。到“还没等到”这句，镜头停在发送端的等待状态，第二次发送从相同位置出发。用本期实验里的业务标识对齐日志，区分“发了几次”和“实际记了几笔”。结尾回到开头两端同框的画面，此时观众应能解释为什么两边可以同时显示不同状态。[table-video 的动作交接](../reference/sources/Table-VideoSOP/skills/table-video/)

**声音与审片。** 给承担解释作用的事件选一个声音，例如回执抵达时的轻响。讲等待时留出听得到的空隙。静音检查每个对象的身份和去向，带声检查“写入”“返回”“超时”分别落在哪一帧。手机上若看不清日志里的标识，先裁出必要的输入与结果，再延长阅读时间。讲 Agent 沙箱时也可沿用这一剪法，把主对象换为本片演示中的文件，跟踪它在哪个工作区创建、何时还能看到。
